## Phase 2 — Core Record-Level Transformations
*Sequential after Phase 1. Internally: Task 2.1 first; Tasks 2.2 and 2.3 both only depend on 2.1 and can then run in **parallel**; Task 2.4 depends on both 2.2 and 2.3, so it runs last.*

- [x] **Task 2.1 — `cntvalid`.** For every form sheet, add a `cntvalid` column (in-memory, on the DataFrames `load_all_data()` returns — not written back onto `Data/all_data.xlsx`) counting answered questions per student using `varname`'s `Ind1==1` columns, excluding 98/99. *(blocks everything else in this phase)*. This augmented per-form data (6 sheets, now carrying `cntvalid`) is also the source for Phase 6 Task 6.1's "export updated `all_data.xlsx`" deliverable — see that task.
- [x] **Task 2.2 — `pop_id` / `pop_id_n` classification** *(parallel with 2.3)*. Implement the group/status decision table in `sppop.xlsx`, including the group-5/6 "did they actually test" branch (needs `cntvalid` from 2.1) and the status-100/600/700 handling.
- [x] **Task 2.3 — Build `TblAllTest`** *(parallel with 2.2)*. Combine every student from every form with `taz_new`, `semel_new`, `MAKBILA_tiyuv`, `code_shelon_rama`, `SIDURY_SHELON`, `cntvalid`, plus `migzar_id`/`pikuach_id`/`machoz_divuach` joined in from `schools.xlsx`. `cntvalid` is computed as `groupby(taz_new).sum()` across all 6 sheets combined (one row per student, summing every row they appear in — within a sheet or across sheets) rather than carried straight from a single row. **Confirmed empirically** (Phase 2 design discussion): in the current data every `taz_new` already appears in exactly one row total, across all sheets — zero duplicates within any sheet and zero `taz_new` overlap between any two sheets — so this sum is a no-op today. It's still implemented as an explicit groupby+sum rather than a straight carry-over, as a deliberate defensive choice in case future/retake data introduces real duplicates. Non-`cntvalid` columns (`semel_new`, `MAKBILA_tiyuv`, `code_shelon_rama`, `SIDURY_SHELON`) take the first value per group — safe under the current one-row-per-student reality, but an assumption to revisit if duplicates ever actually appear.
- [x] **Task 2.4 — `delcodeb` / `delcodeb_n`.** Add to `TblAllTest`, mirroring `pop_id`/`pop_id_n` from 2.2 but forcing blank booklets to `5`; depends on both the classified `sppop` (2.2) and the built `TblAllTest` (2.3).

## Phase 7 — 98/99 Non-Response Code Handling

*Added after the fact, appended here per request. **Sequencing note:** this phase is not actually last chronologically — Task 7.1 and 7.2 must be resolved and implemented **before or alongside Phase 2 Task 2.1** (`cntvalid`), since `cntvalid`'s "98/99 don't count" rule is exactly the policy this phase defines. Task 7.3 is the one piece that's genuinely late (a cross-cutting check, so it fits naturally alongside Phase 5). Listing it here as Phase 7 is a to-do-list convenience, not an execution-order change to Phases 1-6 above — update Phase 2's description once this is implemented, so the plan doesn't contradict itself.*

The task brief says 98/99 "don't count" toward `cntvalid`, but doesn't say what to do with them everywhere else they appear (every `Q*` answer column, including the `Ind1=0` background questions). Leaving them as literal `98`/`99` risks them being silently treated as real numeric answers anywhere other than the one place (`cntvalid`) the brief explicitly calls out — e.g. if anyone later computes a mean/sum/distribution over an answer column.

*Internally sequential: 7.1 → 7.2 → 7.3.*

- [x] **Task 7.1 — Define the policy.** Inspect the real answer-column data to determine whether 98 and 99 carry distinct meanings (e.g. "left blank" vs. "question not applicable to this form/booklet") or are interchangeable "non-response" sentinels for this exercise's purposes. The task brief doesn't disambiguate them — document whatever the data supports, and flag it as an open question for the task-giver if it can't be resolved from the data alone. **Resolved from real data**: 98 and 99 are **not interchangeable** — strongly column-specific (on sheet 472, e.g., `Q6_0`/`Q7_0`/`Q13_0`/`Q18_0` have hundreds of `98`s and almost no `99`s, while `Q19_0`/`Q20_a/b/c`/`Q23_0`/`Q24_0` have zero `98`s and thousands of `99`s; `99` overall is far more common, 16-33% of cells per form vs. 0.3-1% for `98`). This looks like each question's response format has its own fixed invalid-answer convention. The **exact** semantic distinction (e.g. "not administered" vs. "left blank") remains an open question for the task-giver — not resolvable from the data alone, as anticipated.
- [ ] **Task 7.2 — Recode consistently.** Apply the Task 7.1 policy everywhere `Q*` columns are touched (not just in the `cntvalid` calculation) — e.g. recode 98/99 to `NaN` at the loader level (`src/loaders.py`) so no downstream code can accidentally treat them as real answers. Keep the raw unmodified values available too, in case the 98-vs-99 distinction turns out to matter later. **Deliberately deferred, not forgotten** (user decision): investigation showed `cntvalid` already correctly excludes both codes regardless of their distinct meanings, and no other pipeline function (`classify_pop_id`, `build_tbl_all_test`, `add_delcodeb`, `compute_national_norm`, the school report) ever reads an individual `Q*` value — so the only place raw 98/99 is even visible today is `output/all_data_with_cntvalid.xlsx`'s `Q*` columns. Asked the user how that export should handle it (recode in place / export both raw+cleaned / just add a reusable helper); user chose to leave it as-is for now. Revisit this task if/when that export's consumer actually needs the 98-vs-99 distinction resolved.
- [ ] **Task 7.3 — Verify no leakage.** Add a check (pairs naturally with Phase 5's test suite) confirming `cntvalid`, `delcodeb`/`delcodeb_n`, the national-norm count, and the school list are identical regardless of whether 98/99 are represented as literal ints or as `NaN` — i.e. the recoding in 7.2 is safe and doesn't change any already-computed result. Blocked on 7.2 (nothing to verify yet); per the Task 7.2 finding above this would almost certainly pass trivially once 7.2 exists, since no current function reads raw `Q*` values except `cntvalid`'s already-exclusionary count.
